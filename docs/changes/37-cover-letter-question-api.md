## API

| 항목         | 이름        | 규칙                                                                                |
| ------------ | ----------- | ----------------------------------------------------------------------------------- |
| 문항 ID      | `id`        | 이미 저장된 문항만 보냅니다. 새 문항은 비웁니다. 한 목록에 같은 ID가 두 번 오면 400 |
| 문항         | `question`  | 필수, 500자 이하, 앞뒤 공백 제거                                                    |
| 답변         | `answer`    | 선택, 5000자 이하. 빈 값은 `null`                                                   |
| 글자 수 제한 | `charLimit` | 선택, 1~5000의 정수. 없으면 `null`. 답변이 제한을 넘어도 저장합니다                 |

- `GET`은 `{ "questions": [...] }`를 표시 순서대로 돌려줍니다.
- `PUT`의 본문은 `{ "questions": [...] }`이고 최대 10개입니다.
  - 목록 순서가 곧 표시 순서입니다.
  - 목록에 없는 기존 문항은 지우고, `id`가 있으면 고치고, 없으면 새로 만듭니다.
  - 전체를 트랜잭션 하나로 처리합니다. 저장된 목록을 그대로 돌려줍니다.
- `DELETE`는 문항 하나를 지우고 204를 돌려줍니다.
- 오류 응답:

| 상태 | 경우                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------- |
| 400  | 항목 오류. 문항 항목 오류는 "2번째 문항: 문항을(를) 입력해 주세요"처럼 몇 번째 문항인지 앞에 붙입니다 |
| 404  | "지원 기업을 찾을 수 없습니다", "자기소개서 문항을 찾을 수 없습니다"(다른 기업의 문항도 포함)         |
| 409  | `PUT`에 다른 기업의 문항이나 그사이 지워진 문항의 `id`가 있을 때. 아무것도 바꾸지 않습니다            |

## 판단한 내용

- **목록을 한 번에 저장합니다.** 화면(#51)에서 문항을 추가·삭제·순서 변경한 뒤 한 번에 저장하므로, 요청 하나를 트랜잭션 하나로 처리해 일부만 저장되는 일을 막습니다.
- **본문 한도에 맞춰 개수와 길이를 정했습니다.** 답변 5000자 10개는 한글로 약 150KB입니다. 서버의 JSON 본문 한도 256KB 안에 들어갑니다. 처음 추천한 "답변 10000자, 문항 20개"는 이 한도를 넘을 수 있어 줄였습니다.
- **순서는 기업 안에서 겹치지 않게 DB가 막습니다.** 다만 검사는 커밋할 때 합니다(`DEFERRABLE INITIALLY DEFERRED`). 그래서 저장 한 번으로 두 문항의 자리를 맞바꿀 수 있습니다.
- **바뀐 문항만 `updated_at`이 갱신됩니다.** 같은 목록을 다시 저장해도 행을 건드리지 않습니다. 나중에 이전 버전 보관을 붙일 때 기준이 됩니다.
- **동시 저장:** 문항을 바꾸는 `PUT`과 단건 `DELETE`는 모두 먼저 지원 기업 행을 `FOR UPDATE`로 잠급니다. 같은 기업의 목록 저장, 문항 삭제, 기업 삭제가 겹치면 차례로 처리됩니다. 그래서 단건 `DELETE`도 대상 기업이 없으면 "지원 기업을 찾을 수 없습니다"로 404입니다.
- **삭제 확인 창의 문항 수**(#49)는 별도 필드를 만들지 않습니다. 화면이 문항 조회 API로 셉니다.
- **통합 테스트 잠금:** 테스트 파일은 여러 프로세스에서 동시에 돕니다. 지원 기업 테스트가 `DELETE FROM applications`를 하면 문항 테스트의 데이터까지 지워집니다. 그래서 두 파일이 같은 advisory lock을 잡습니다.
- **마이그레이션 번호:** `008`을 예약했습니다.

## 검증

이 PC의 Docker에 띄운 PostgreSQL 17(`postgres:17-alpine`)에서 확인했습니다.

- `001`~`008`을 `career_test`에 차례로 적용: 모두 종료 코드 0. `008`을 한 번 더 적용하면 `relation "cover_letter_questions" already exists, skipping` 알림만 나왔습니다.
- `TEST_DATABASE_URL`을 `career_test`로 두고 `npm run check`: 통과(종료 코드 0).
  - 백엔드 86건 통과·건너뜀 0건.
  - 새 테스트는 단위 6건, DB 통합 2건입니다.
  - 프론트엔드 166건 통과·2건 건너뜀(기존 테마 조건부 테스트). 스킬 검사 4건 통과.
- `npm run knip`: 통과.
- 통합 테스트가 확인하는 것:
  - 기업별 분리.
  - 빈 답변·제한 없음은 `null`이고, 제한을 넘은 답변도 저장됩니다.
  - 저장 한 번으로 순서 맞바꾸기, 수정, 삭제, 추가가 됩니다. 같은 목록을 다시 저장하면 `updated_at`이 그대로입니다.
  - NUL 문자가 든 문항에서 실패하면 앞선 수정·삭제까지 모두 되돌립니다.
  - 다른 기업의 문항 ID는 409이고, 두 기업 모두 그대로입니다.
  - 문항 하나를 삭제할 수 있고, 다른 기업 경로로는 404입니다.
  - 기업을 삭제하면 문항도 사라집니다. 없는 기업은 404입니다.
  - DB 제약(빈 문항, 제한 0·5001, 음수 순서, 순서 중복)을 확인합니다.

첫 실행에서 기존 테스트 1건이 `fetch failed: bad port`로 실패했고, 다시 실행하니 통과했습니다. 이 변경과는 관계없습니다. 테스트 서버가 `listen(0)`으로 받은 포트가 fetch가 막는 포트(예: 6000)일 때 생기는 일입니다. 별도 이슈로 분리합니다.
